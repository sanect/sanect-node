# Generated EVM verifier

This directory holds **`Verifier.sol`** — the on-chain UltraHonk verifier
generated by `bb write_solidity_verifier` from our Noir circuit's
verification key. It's roughly ~77 KB of generated assembly.

## Status

- The actual `Verifier.sol` is **generated locally** by the developer
  and committed alongside its hash in `../manifest.json`. We don't
  regenerate it on every CI run because:
    1. The circuit source + bb version + nargo version are pinned, so
       byte-identical regeneration is guaranteed.
    2. Generating it requires the full bb toolchain, which we don't want
       to install in every CI image.
- CI (and `scripts/verify-chain.sh`) instead reads `manifest.json` and
  asserts the on-disk file's SHA-256 matches what was committed.

## Regenerating it (any developer, after editing the circuit)

```bash
cd ~/sanect-node/privacy/circuits/transfer

# 1. Compile the circuit
nargo compile

# 2. Write the verification key
mkdir -p target/vk
bb write_vk -b target/transfer.json -o target/vk

# 3. Write the Solidity verifier
bb write_solidity_verifier -k target/vk/vk -o ../verifier/Verifier.sol

# 4. Update the manifest (SHA-256 + commit hash + toolchain versions)
cd ../../..
node scripts/build-manifest.js privacy/circuits/manifest.json
```

After step 4, `git diff manifest.json` should show one updated hash;
commit that alongside any circuit changes.

## What's in the file

- `HonkVerificationKey` library — circuit-specific constants (the
  proving key encoded as G1/G2 points).
- `BaseHonkVerifier` abstract contract — the verification algorithm
  proper, identical across all UltraHonk circuits.
- `HonkVerifier` contract — concrete deployable contract that pairs
  the base verifier with our specific VK.

You don't read or hand-edit any of this. The pool calls
`HonkVerifier.verify(proof, publicInputs)` and trusts the result.

## What the pool sees

Our `IVerifier.sol` declares:

```solidity
function verify(bytes calldata proof, bytes32[] calldata publicInputs)
    external view returns (bool);
```

That signature matches `HonkVerifier`'s `verify(bytes, bytes32[])`
exactly — same selector, same calling convention. We can cast a
deployed `HonkVerifier` address to `IVerifier` in the pool and call
straight through.

## Public inputs the chain sees

The bb-generated verifier has `NUMBER_OF_PUBLIC_INPUTS = 8`, in this
exact order (must match the Noir circuit's `pub Field` declaration
order):

```
[ input_nullifier_0,
  input_nullifier_1,
  output_commitment_0,
  output_commitment_1,
  merkle_root,
  public_amount,
  public_asset,
  public_recipient ]
```

`ShieldedPool._packPublicInputs()` packs the same 8 fields in the same
order from its typed arguments before calling the verifier.

## Bytecode size

`Verifier.sol` compiled is roughly 24 KB (just under the EIP-170 limit).
If a circuit change pushes it over, we have two escape hatches:

1. Split the verifier into a small dispatcher + a heavy library called
   via `delegatecall`.
2. Use `bb`'s `--zk` flag (smaller proofs, slightly larger verifier —
   usually a wash on bytecode size but a different trade-off).

For the v1 circuit (6307 gates, 8 public inputs) we're well inside the
limit.
