# Keys, slashing, and how not to lose stake

A validator on sanect has **two** keys that matter, plus a small piece of
state that's just as critical:

| Thing | File on disk | Loss / leak consequence |
|---|---|---|
| **Consensus key** (signs blocks) | `priv_validator_key.json` | Anyone with this can double-sign on your behalf → 5% slash + tombstone (permanent removal). Losing it: you must create a new validator from scratch. |
| **Operator key** (signs txs: create-validator, withdraw rewards, edit description) | keyring (`~/.sanectd/keyring-*`) | Anyone with this can move your unbonded balance, change commission, etc. |
| **Last signed state** | `priv_validator_state.json` | Rolling this backwards = signing a height you already signed at a different hash = **double-sign**. |

This document covers all three.

## Slashing conditions on sanect

From genesis params:

| Condition | Trigger | Penalty |
|---|---|---|
| **Double-sign** (equivocation) | Two different votes at the same height/round by the same key | `slash_fraction_double_sign = 5%` + **tombstoned** (can never validate again with this key) |
| **Downtime** | Miss > 50% of blocks in the `signed_blocks_window` of 100 | `slash_fraction_downtime = 1%` + jailed for `downtime_jail_duration = 600s` (unjail tx required after) |

Downtime is annoying but recoverable. Double-sign is final — operationally
treat your validator key like the seed phrase of a treasury wallet.

## Consensus key (`priv_validator_key.json`)

This is generated by `sanectd init` and lives in the node's home:

```
/data/.sanect/config/priv_validator_key.json
```

It's a 32-byte ed25519 key. The whole file is small (~300 bytes JSON) and
**immutable for the life of the validator**. You can't rotate it without
retiring the current validator and creating a new one (different
`valoper` address).

### Back it up once, properly

The minute the validator first starts, copy `priv_validator_key.json` to a
**cold, offline** location:

- Print the JSON on paper, lock it in a safe. (Yes, paper. Ed25519 keys are
  short enough.)
- Or: write it to two encrypted USB drives, store them at different physical
  locations.
- Encrypted backup format we use internally: `age -p < priv_validator_key.json > backup.age`.

Do NOT:
- Commit the key to git, ever.
- Email it / Slack it / Notion it.
- Store the only copy on the same disk as the running node. If the disk dies
  you lose the validator.

### Recovering a key (legitimate)

If your validator host dies, the recovery is:

1. **Verify nothing else is signing** with this key right now. If your host
   was already running, make sure it stays off. Two nodes signing = slash.
2. Provision a new host (same provider or new — provider doesn't matter
   for the key).
3. Restore `priv_validator_key.json` from your backup into
   `/data/.sanect/config/`.
4. Restore `priv_validator_state.json` if you have it (see next section);
   if you don't, the safe move is to wait out a few blocks before starting,
   then start with `--unsafe-skip-upgrades` only if you're sure. **Do not
   resume signing without `priv_validator_state.json` matching the current
   chain tip** — see the next section.
5. Sync the chain (state sync or full sync), then start the node.

## `priv_validator_state.json` — the underrated file

```
/data/.sanect/data/priv_validator_state.json
```

Tracks the highest `(height, round, step)` your key has signed at, plus the
signature. CometBFT refuses to sign at or below this height/round/step. This
is what stops your node from re-signing if you reboot mid-block.

### The double-sign trap

```
State on disk: signed (height=100000, round=0, step=PRECOMMIT)
Chain at:      height 100100
You restore an OLD volume backup: state shows height=99000
You start the node
→ Node sees the chain at 100100, starts signing forward
→ At some point you re-process height 99500 (sync), state says "fine, 99000 < 99500, sign it"
→ But at height 99500 the chain originally committed hash X; with your key it now signs hash Y
→ Equivocation evidence eventually reaches the chain → 5% slash + tombstone
```

Rules:
- **Never restore an old `priv_validator_state.json`** without also
  restoring the matching block data.
- If recovering from key backup only, the safest move is to **not sign for
  one full `signed_blocks_window` (100 blocks)** while the chain commits
  past any height you might have signed. Practically: start the node with
  the validator unbonded or the key removed, sync to tip, then re-bond.
- For high-stake setups, use **TMKMS** (below) which keeps state on a
  separate machine that can never be rolled back accidentally.

### A safe "double-sign protection" file

A nuclear belt-and-suspenders option: deliberately set
`priv_validator_state.json` to a height **higher than the current chain tip**
before starting recovery. The node will refuse to sign until the chain
catches up. Format:

```json
{
  "height": "999999999",
  "round": 0,
  "step": 0
}
```

Then once the chain is past where you might have signed, replace this with
an empty state (`{"height":"0","round":0,"step":0}`) and the node will
resume normally.

## Operator key (`mykey` in the keyring)

This is the EVM/Cosmos key that signs **transactions** like
`MsgCreateValidator`, `MsgEditValidator`, `MsgDelegate`,
`MsgWithdrawDelegatorReward`. It's separate from the consensus key.

```
~/.sanectd/keyring-file/   # or keyring-os, keyring-test, keyring-pass
```

For production:
- **Never use `--keyring-backend test`.** It stores keys unencrypted on disk.
  Fine for the local devnet; never for a real validator.
- Use `--keyring-backend file` (encrypted file with a passphrase) or
  `--keyring-backend os` (system keychain) on the ops machine. The validator
  *host* doesn't need this key — only your ops/admin laptop does.
- For mainnet later: hardware wallet for the operator key (Ledger via
  `--ledger` flag).

### Separation of duties

A clean setup:

```
[ops laptop / hardware wallet]  ← operator key. Signs delegate / withdraw txs.
        |
        | broadcasts signed tx through any RPC
        v
[validator host / sentry / TMKMS]  ← consensus key only. Signs blocks.
```

The validator host should **not** have the operator key. If it's
compromised, the attacker shouldn't be able to drain rewards or change
commission.

## Hardware-grade signing: TMKMS

For real money, run the consensus key in
[**TMKMS**](https://github.com/iqlusioninc/tmkms) on a separate machine
(ideally with a YubiHSM or Ledger). The validator's
`priv_validator_key.json` is replaced with a connection to TMKMS:

```toml
[priv_validator]
laddr = "tcp://<tmkms-host>:26659"
```

Benefits:
- The consensus key never lives on the validator host.
- TMKMS keeps a robust local state file that protects against double-sign
  even across crashes / volume rollbacks.
- One TMKMS instance can serve a primary + standby validator pair (with
  failover) without risking double-sign — it serializes signing decisions.

This is what every serious Cosmos validator runs. For sanect
today it's overkill, but plan to enable it before mainnet.

## Key rotation

You cannot rotate the consensus key in place. Rotation = retire the
current validator and create a new one:

1. From the operator key: `sanectd tx staking unbond <valoper> <amount>` to
   move stake out.
2. Wait `unbonding_time` (1814400s = 21 days on sanect).
3. `sanectd tx staking create-validator` with a fresh consensus key on a fresh
   node. New `valoper` address, new everything.

Delegators have to manually move stake to the new validator. There is no
in-place validator key rotation in cosmos-sdk today.

The operator key (regular wallet) CAN be rotated — just transfer your
operator's balance to a new account. But the `valoper` address stays tied
to the original.

## Quick "before going live" checklist

- [ ] `priv_validator_key.json` backed up to **two** offline locations.
- [ ] Operator key is in `--keyring-backend file` or `os`, not `test`.
- [ ] Operator key backup phrase written on paper, stored separately from
      the consensus key.
- [ ] Only **one** node has this consensus key loaded right now.
- [ ] Volume has **automatic snapshots disabled** at the provider level,
      OR you've documented the snapshot/restore procedure to NEVER restore
      `priv_validator_state.json` from a snapshot. (Restoring it backwards
      = double-sign.)
- [ ] Monitoring alerts include: "validator signing rate dropped" and
      "validator jailed".
- [ ] You know which person on your team is on-call for outages.

See [`runbook.md`](./runbook.md) for what to do when something goes wrong.
